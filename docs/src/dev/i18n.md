# i18n and Arabic

Arabic is a first-class language in TLP-Desk, not a translation added later. A feature that shows,
stores or sends text is not done until it works in Arabic: shaping, bidi, right-to-left layout and
UTF-8/UTF-16 paths. This page explains how the GUI does it and the rules for adding UI.

The code lives in `crates/tlp-desk-app/src/i18n/` (`mod.rs`, `shaping.rs`, `format.rs`) and
`ui/theme.rs` / `ui/widgets.rs`.

## The string table

Every user-facing string is one entry in the `strings!` macro in `i18n/mod.rs`:

```rust
strings! {
    // Home — this device
    DeviceId => "Device ID", "معرّف الجهاز";
    OneTimeCodeHint => "Share it only with someone you trust.", "لا تشاركه إلا مع شخص تثق به.";
    Connecting => "Connecting to {target}…", "جارٍ الاتصال بـ {target}…";
}
```

The macro generates `enum S` (one variant per key) and two parallel arrays, `EN` and `AR`.
Because each entry *must* have both strings, **a missing translation is a compile error**. Tests
add more guarantees:

| Test | Checks |
|---|---|
| `every_key_has_english_and_arabic` | No empty strings; Arabic text contains RTL letters (except brand keys such as `AppTitle`); English contains no Arabic |
| `placeholders_match_between_languages` | `{name}` placeholders are identical in both languages |
| `arabic_display_strings_are_prepared_once` | The Arabic table is shaped once and cached |

### Adding a string

1. Add `MyKey => "English", "العربية";` in the right section of `strings!`. Write natural Modern
   Standard Arabic — not a word-by-word translation — and keep placeholders (`{name}`) identical.
2. Use it through `Tx` (below), never as a literal in UI code.
3. Run `cargo test -p tlp-desk-app i18n`.
4. If the text can contain user data (names, paths, addresses), add a test with Arabic and mixed
   Arabic/Latin/digits input.

## `Tx`: the one display helper

UI code receives a small `Copy` value `Tx { lang, digits }` and calls:

| Method | For | Example |
|---|---|---|
| `t(S)` | Static string, ready to display | `ui.label(tx.t(S::DeviceId))` |
| `f(S, &[("name", value)])` | Template with arguments | `tx.f(S::Connecting, &[("target", &target)])` |
| `d(text)` | Dynamic text (device names, error details); direction from the text itself | a peer's name |
| `p(text)` | Logical text in the UI's paragraph direction | "12 ms" |
| `digits(text)` | A number/ID/IP *inside* a sentence: digit style + LTR isolate | an ID in a template argument |
| `n(text)` | A standalone number/ID/code/IP: digit style, always left-to-right | the big device ID |
| `raw(S)` | Logical order, for text rendered by Windows (window title) or further templating | |
| `rtl()` | Is the UI right-to-left? | layout decisions |

**Rule: every piece of text is shaped exactly once.** Do not pass the output of `t`/`f`/`d` into
another `Tx` method.

## Why shaping and bidi are done by hand

egui 0.36 shapes each font run correctly (contextual letter forms, lam-alef ligatures, harakat
positioning), but it has **no Unicode Bidirectional Algorithm**: runs are laid out left to right in
string order. An Arabic sentence would therefore show its words in reverse order, and mixed
Arabic/English/IP text would be scrambled (the test `egui_without_our_bidi_gets_word_order_wrong`
demonstrates it).

`shaping.rs` fixes this before egui sees the text:

1. `unicode_bidi::ParagraphBidiInfo` resolves embedding levels for the line.
2. Right-to-left runs are reversed by grapheme cluster (so harakat stay with their letter), and
   brackets are mirrored.
3. Runs that will be drawn with the Arabic font are pre-reversed once more, because egui's shaper
   reverses them again.
4. LTR isolates (LRI…PDI) — used for IDs, codes and IPs inside Arabic sentences — are swapped for
   placeholder characters during reordering and pasted back left to right, so `١٢٣ ٤٥٦ ٧٨٩` keeps
   its group order.

The output is a permutation of the input with bidi controls removed. Text without RTL characters
is returned borrowed and unchanged. The `egui_*` tests lay text out with the real epaint pipeline
and the bundled fonts and check glyph positions.

**Known limitations**

- Reordering works per explicit line (`\n`). In RTL, labels use `wrap_mode = Extend`, so they do
  not soft-wrap; keep Arabic labels short or split them yourself.
- **Text fields while typing:** egui's `TextEdit` edits the logical string with a left-to-right
  caret. Fields with Arabic text (`ui::widgets::text_field`, the chat box, address-book notes)
  therefore switch to `ui::bidi_edit::BidiEdit`, which keeps the logical string but lays it out
  in screen order and moves the caret and selection on screen. The model (`bidi_edit/model.rs`)
  is egui-free and unit-tested; a caret at a boundary between left-to-right and right-to-left
  runs has two possible places and the arrow keys visit both. No IME pre-edit string is shown
  while such a field is active. See [ADR 0007](../adr/0007-egui-with-bidi-workaround.md).

## Fonts

Noto Sans Arabic Regular (SIL OFL) is embedded and added as a fallback to both the proportional
and monospace families, slightly scaled (×1.08) to match the Latin UI font. Its licence is shipped
in the installer's `licenses` folder.

## Digits

Settings offer **Western (0-9)** or **Arabic-Indic (٠-٩)** digits for display (`DigitStyle`).

- `format::localize_digits` converts for display; Arabic-Indic uses `٫` as the decimal and `٬` as
  the thousands separator.
- `format::to_western_digits` converts both Arabic-Indic (`٠-٩`) and Eastern Arabic-Indic
  (`۰-۹`) digits back. Every input field that takes an ID, code or address runs it first.
- **IDs, codes and addresses are always copied to the clipboard with Western digits**, whatever
  the display setting, so they paste correctly everywhere.
- `number`, `bitrate`, `file_size` and `duration` format values in logical order; display them
  through `Tx`.

## Right-to-left layout

- `theme::row` lays out right-to-left in Arabic; `row_end` is its mirror; `column` aligns to the
  right edge.
- Never hard-code left/right. Use the theme helpers so layouts mirror automatically.
- Two-column screens swap their columns; overlays move to the other corner (the stats overlay is
  top-left in Arabic).
- Direction-bearing icons are mirrored. The chevron on buttons is *painted*, not a font glyph, so
  it can be flipped.
- Text fields are right-aligned in RTL.

## Language selection

`Lang::detect()` reads the Windows UI language on first run (`ar*` → Arabic, anything else →
English). The choice is saved in `settings.json` and can be changed live from the language menu or
Settings; `--lang ar|en` overrides it for one run.

## Beyond the GUI

- The **CLI** keeps its strings in `tlp-desk-cli/src/text.rs` (English only for now; `--lang` and
  UTF-8 console output are on the roadmap).
- **Device names** travel as UTF-8 in mDNS TXT records and broadcast packets (at most 64
  characters); round-tripping Arabic names through discovery is still to be verified.
- **Paths** (file transfer) stay UTF-8 in the protocol and become UTF-16 only at the Windows API
  boundary.
- The **installer** ships Arabic and English wizard languages.

See also the "Arabic and i18n" section of the [code style guide](conventions.md).
